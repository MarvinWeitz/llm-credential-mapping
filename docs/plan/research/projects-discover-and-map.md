# discover-and-map
## VERDICT
Projects do work with SSO, just not directly. The SSO session token never carries a project_id, so calls made with it count only toward the user and team. To get per-project attribution, the CLI uses the session token to look up the project and then mints a short-lived virtual key tied to that project. Nobody handles that key by hand. At 10444df the answers are: (a) YES. Any member of a team, including an internal_user_viewer, can call GET /project/list and /project/info with a session token. List returns every project of every team the user belongs to. (b) YES. The full project row comes back, including the free-form metadata. So metadata.repositories = ["github.com/acme/smart"] and metadata.customer = "X" are readable and the CLI can match the Git origin with no prompt. (c) Only two roles can create or update projects. A proxy admin always can. A team admin of the project's team can only if the proxy sets general_settings.team_admin_editable_team_fields to include "projects". Both also need an enterprise (premium) license. Ordinary members and org admins cannot, and only a proxy admin can delete. Key reuse works only if the CLI keeps its own copy: the database stores only the key's hash. With that copy, /key/info (own keys) and /key/list?project_id=...&status=active (scoped to the caller) can confirm the key is still active, which avoids minting duplicates. Two one-time settings are easy to miss: SSO users get the internal_user_viewer role by default, which cannot call /key/generate, and plain team members cannot call /key/generate until the team's team_member_permissions allow it. Upstream main (d364d5e) does not change any of this, except that org admins can now also read projects.

## RISKS
- Attribution relies on the client. /key/generate never checks that project.team_id matches the key's team_id or that the caller belongs to the project's team (key_management_endpoints.py:1764-1811, 2139-2146). A team member could tie their key to another team's project if they know its project_id. Treat attribution as trusted-client unless a custom key-generate hook enforces it (key_management_endpoints.py:2070-2081).
- The minted sk- keys are separate from the SSO session. Signing out (lite logout) or deactivating the user in SSO does not revoke them; the refresh flow only stops new session tokens. Use a short duration (24h or less, matching LITELLM_CLI_JWT_EXPIRATION_HOURS) and consider a server-side duration cap. I did not trace whether request-time auth re-checks team membership for an existing team key (inferred).
- Users created through SSO default to internal_user_viewer (ui_sso.py:1996-1998). They can list and read projects but get a 403 on /key/generate. Without the role fix, the flow breaks at key minting.
- Default team_member_permissions only allow /key/info and /key/health, so plain members cannot mint team keys until a team admin or proxy admin adds /key/generate. Without /key/delete they also cannot clean up old team keys.
- /project/update replaces metadata wholesale and can silently drop per-model rpm/tpm limits stored there. Any tool that maintains the repo mapping must read, modify and write back the full metadata.
- Every team member can see the whole project row: metadata, budget, spend and object_permission. Do not store secrets in project metadata.
- /project/list decides membership from LiteLLM_UserTable.teams, while /project/info uses team.members_with_roles (project_endpoints.py:1078-1086 vs 1016-1024). If SSO team sync updates one without the other, the two can disagree (inferred).
- key_alias is unique across all keys, expired ones included (key_management_endpoints.py:7800-7830). Use a timestamped alias or delete old keys.
- If one repo appears in several projects' metadata.repositories (for example a monorepo serving several customers), the CLI cannot pick automatically. A repo-local override file or a one-time prompt would be needed (inferred design gap).
- Project management is marked Beta and Enterprise in the docs. Create, update and delete need premium_user, and the routes exist only when litellm_enterprise is installed.
- The UI setting text claims org admins are 'not affected', but org admins cannot manage projects at 10444df or on upstream main. Upstream main only adds org-admin read visibility.
- Process note: one git grep over tests/ in the blob:none partial clone made git lazily fetch blobs (and auto-pack) in the scratch repo's object store before I stopped it. The working tree and refs were not changed (git status clean). Upstream comparison used git ls-remote and raw.githubusercontent.com downloads into the scratchpad. The GitHub API and MCP were not available for BerriAI/litellm in this session.

## REVIEW verdict_holds=yes
### CORRECTED VERDICT
The verdict holds. LiteLLM Projects can be used with CLI SSO, but only indirectly. At 10444df the session token never has a project_id (litellm/proxy/auth/auth_checks.py:3806-3825). Nothing resolves a project from a request header or JWT claim either: the JWT path at user_api_key_auth.py:1872-1883 only reads valid_token.project_id, which comes from a key. So per-project attribution needs an sk- key bound to a project_id. The CLI can mint and cache that key itself with the SSO session token, so nobody handles keys by hand.

(a) Yes. /project/list and /project/info are in self_managed_routes (_types.py:1005-1006), and that branch has no role condition (route_checks.py:350-358), so any authenticated role passes the route check, including internal_user_viewer. /project/list returns every project whose team is in LiteLLM_UserTable.teams (project_endpoints.py:1059-1088). /project/info requires the caller to be in members_with_roles (:999-1024). Neither endpoint has a premium check.

(b) Yes. The full row is returned, including free-form metadata, so metadata.repositories and metadata.customer can drive automatic matching against the Git origin.

(c) Create and update require a license (premium_user, project_endpoints.py:485-498). Beyond that, only a proxy admin can do them, or a team admin of that team when general_settings.team_admin_editable_team_fields contains "projects" (:83-118; team_admin_field_permissions.py:72-100; the default is empty). Only a proxy admin can delete. /project/update replaces metadata wholesale (:784-841).

Minting has two default blockers. First, SSO-created users default to internal_user_viewer, and that role lacks /key/generate. Second, the default team_member_permissions are only /key/info and /key/health (team_member_permission_checks.py:18-21).

Key reuse works only if the CLI keeps the plaintext key itself. /key/list is scoped to the caller (key_management_endpoints.py:6658-6660) and filters by project_id and status.

The main correctness caveat stands: neither /key/generate (:2139-2146) nor request-time project checks (auth_checks.py:742-786: blocked, models, budget only) verify that project.team_id matches the key's team. Attribution therefore trusts the client.

One nuance needs correcting. litellm.default_internal_user_params only sets the role of newly inserted SSO users (ui_sso.py:2630-2645 via insert_sso_user). Existing users who already have internal_user_viewer in the database keep it unless the IdP supplies a valid role (ui_sso.py _build_sso_user_update_data). Those users need an IdP role mapping, jwt_litellm_role_map with sync_user_role_and_teams, or a one-time /user/update by an admin.

Upstream main is still d364d5e as of 2026-10-07 (git ls-remote). There, /project/info and /project/list also admit org admins of the team's org (_can_view_team_projects, upstream project_endpoints.py:123-139, 1046, 1101). Create, update, delete and the premium gates are unchanged.
