AREA: auth

## CURRENT ASSESSMENT
- The project is built on the right primitive. LiteLLM's native CLI SSO contract (discovery, DCR, PKCE S256, loopback, rotating refresh, RFC 7009 revoke) gives employee/team-scoped credentials with no sk- keys and no admin key. The client is strict and careful: discovery endpoints are pinned to the configured origin, redirects are refused, state is compared in constant time, and returned team/user are checked against the profile at login and at every refresh (revoking an unexpected grant). Re-login revokes the previous grant.
  IMPACT: Meets goal 3 (SSO, no key rotation). The security posture is better than LiteLLM's own `lite` client in several places (expected-team check, no redirects, strict schema). Keep this foundation.
  FILES: src/virtual_key_mapper/litellm.py:39-71, 104-109, 286-312; src/virtual_key_mapper/transport.py:118-121,154; src/virtual_key_mapper/sessions.py:32-51
- Known lockout bug, confirmed. `SessionManager.token()` writes `refresh_pending=True` to the vault before any network I/O (sessions.py:67-68). `LiteLLMClient.refresh()` then does a discovery GET before the token POST (litellm.py:287). Any CredentialError (DNS, Wi-Fi drop, TLS, HTTP 503) leaves `refresh_pending` set. Every later call fails with 'log in again' (sessions.py:61-62), even though the refresh token was never sent. `revoke()` also re-runs discovery (litellm.py:315), so logout fails on a discovery hiccup.
  IMPACT: A transient network blip forces a browser re-login and kills running Claude extension sessions and the Copilot bridge. This breaks the 'just works' goal. LiteLLM's own client avoids this by storing token_endpoint, revocation_endpoint and resource in the credential record and never re-discovering on refresh.
  FILES: src/virtual_key_mapper/sessions.py:61-72; src/virtual_key_mapper/litellm.py:286-298, 314-321
- The refresh-failure policy is stricter than the server needs, and it treats retryable errors as fatal. In LiteLLM's native grant code the single-use refresh marker is claimed after the user is re-validated and the credential is minted. Database or Redis outages therefore return 503 and leave the refresh token valid. The docs say the CLI should 'keep the key it already has and try again'. A replayed native refresh token only gets 400 invalid_grant; the grant is not revoked. Grant revocation on reuse applies only to 'hosted app' grants. So retrying after an uncertain response can never do worse than the current forced re-login.
  IMPACT: The 'uncertain renewal requires re-login' rule (README:281-287) copies the hosted-app guidance but applies it to native grants. Safe retry rules would remove almost all lockouts with no security cost.
  FILES: src/virtual_key_mapper/sessions.py:61-83; README.md:274-287
- Refresh happens only within 60 s of expiry (sessions.py:63). A failed refresh therefore leaves essentially no usable access token. On the `run` path, `launch()` injects whatever token `token()` returns as a static env var (cli.py:330 -> agents.py:99-104,107,115,140). An agent can start with as little as 61 s of validity left, and nothing renews it afterwards (README:239-242).
  IMPACT: Codex, OpenCode and Claude CLI sessions launched near token expiry die within minutes. Long sessions die at expiry (24 h by default, or sooner if the admin shortens the lifetime). This is the main renewal gap for goal 2.
  FILES: src/virtual_key_mapper/sessions.py:63; src/virtual_key_mapper/agents.py:93-151; src/virtual_key_mapper/cli.py:316-330
- Lock contention can cause spurious failures. The per-profile FileLock times out after 10 s (profiles.py:336). A refresh holds that lock across two network calls with 20 s timeouts each (transport.py:154), plus keyring I/O. Concurrent callers (Claude apiKeyHelper every 60 s per session, the Copilot bridge per request, CLI launches) give up with 'Another credential operation is busy' during a slow refresh.
  IMPACT: Claude's helper exits 1. Claude retries once and then surfaces an error. The bridge returns 503. These are intermittent failures that are hard to diagnose.
  FILES: src/virtual_key_mapper/profiles.py:332-341; src/virtual_key_mapper/transport.py:154; src/virtual_key_mapper/claude.py:191-198,271; src/virtual_key_mapper/copilot_bridge.py:240-246
- Storage is OS-keyring only. Only an allowlist of keyring backends is accepted, with no fallback (storage.py:30-57). Headless Linux, WSL without Secret Service, Dev Containers, Codespaces and SSH remote hosts are unsupported (README:703-705). The Claude extension adapter must run where the extension host runs, which is inside the container for Remote-Containers (README:292-297).
  IMPACT: Remote and container development, including the Claude VS Code extension in a devcontainer, does not 'just work'. Every mature CLI surveyed (gh, lite, kubelogin, az on Linux/macOS, AWS SSO) either falls back to an owner-only file or offers an explicit alternative store (Git Credential Manager: cache/gpg/plaintext; kubelogin: disk/keyring/none).
  FILES: src/virtual_key_mapper/storage.py:23-57; README.md:292-297, 701-705
- Login only works on the machine running the browser. The callback listener binds 127.0.0.1 on the CLI host (litellm.py:184-189). `--no-browser` only prints the URL (litellm.py:264-265) and cannot accept the redirect URL pasted back. LiteLLM's native contract refuses non-loopback redirects and does not support the device authorization grant.
  IMPACT: On SSH hosts, devcontainers and Codespaces the user has to set up a manual `ssh -L` port forward or cannot log in. This adds friction and makes remote setups fail.
  FILES: src/virtual_key_mapper/litellm.py:133-199, 218-284
- 'Short-lived' depends on the server. The native access token's `expires_in` is `CLI_JWT_EXPIRATION_HOURS*3600` (default 24 h). It is a stateless credential that can be neither revoked nor rotated mid-session. Refresh tokens rotate, are single-use and last 14 days (sliding: each renewal issues a fresh one and re-checks the user and team membership). Multi-worker gateways need Redis for single-use and revocation, and fail closed with 503 when Redis is down.
  IMPACT: With defaults, a leaked access token is valid for up to 24 h and offboarding takes up to 24 h. Admins should set LITELLM_CLI_JWT_EXPIRATION_HOURS lower (integer hours, minimum 1). That only works if all agents renew transparently, which today only the Claude extension and the Copilot bridge do.
  FILES: README.md:120-141 (doc claims); upstream: litellm/proxy/_experimental/mcp_server/proxy_api_credentials.py:81, outbound_credentials/session_token.py:71
- Contract stability. The `/.well-known/litellm-cli-auth` contract is explicitly versioned (`contract_version: 1`; adding fields does not bump it). Its implementation lives under `litellm/proxy/_experimental/mcp_server/`. LiteLLM's docs still label 'CLI SSO Authentication' as beta and say it needs EXPERIMENTAL_UI_LOGIN. The `lite` CLI README in the source tree says EXPERIMENTAL_UI_LOGIN is not required on a default deployment. Any SSO for more than 5 users needs a LiteLLM Enterprise license.
  IMPACT: Pinning to contract v1 and rejecting other versions is correct (litellm.py:41-42), but expect churn. Licensing does not distinguish the options: native CLI SSO and JWT/OIDC auth both need Enterprise at company scale.
  FILES: src/virtual_key_mapper/litellm.py:28-71; README.md:43-66

## OPTIONS
### [adopt/high] A. Harden the existing native-contract client
 interaction: one-time per machine (login per profile; re-login only after 14 days idle, deprovisioning or explicit logout)
 providers: All (foundation for every adapter)
 sso: True
 renewal: Renewal itself becomes reliable; delivery to agents still needs option B
 how: Same LiteLLM `/.well-known/litellm-cli-auth` v1 contract. Changes: (1) store token_endpoint, revocation_endpoint, resource and client_id in the Session at login and never re-discover on refresh or revoke. (2) Classify refresh failures. Connect/DNS/TLS errors before sending, HTTP 429/5xx/503 (LiteLLM's documented 'temporarily_unavailable') and timeouts: keep the stored refresh token and back off. Only 400 invalid_grant or 401 invalid_client mark the grant dead. A retried, already-spent native refresh token only gets invalid_grant, so retrying is safe. (3) Refresh early: when remaining lifetime is under max(10 min, 25 % of lifetime) and before every agent launch if under ~1 h. A failed refresh then still leaves a valid token, and the next call retries. LiteLLM's own client uses a 360 s buffer. (4) After taking the lock, re-read the vault to pick up a sibling's rotation. Make the lock wait longer than the worst-case refresh time (two 20 s timeouts plus keyring I/O), or use shorter network timeouts. (5) Remote login: `--no-browser` accepts the pasted final redirect URL (state-checked), the pattern used by kubelogin `authcode-keyboard` and gcloud `--no-launch-browser`.
 pros: ['Fixes the lockout bug and most intermittent failures without changing the architecture', 'Keeps SSO, rotating refresh and no keys', "Brings the client in line with LiteLLM's own reference client and its documented 503 retry semantics", 'Paste-back login makes SSH, devcontainer and Codespaces login possible with no server change']
 cons: ['Still bound to a beta, `_experimental` server implementation', 'Paste-back login adds one manual copy step on remote hosts']
 sources: ['https://github.com/BerriAI/litellm-docs/blob/main/docs/proxy/cli_sso.md (published at https://docs.litellm.ai/docs/proxy/cli_sso)', 'https://github.com/BerriAI/litellm/blob/main/litellm/proxy/client/cli/commands/pkce_login.py (fresh_api_key, pkce_token_record)', 'https://github.com/BerriAI/litellm/blob/main/litellm/proxy/_experimental/mcp_server/gateway_dcr_flow.py (_GrantIssuer, _refresh_token_grant, _SingleUseGuard)', 'https://github.com/int128/kubelogin/blob/master/docs/usage.md']

## RECOMMENDATION
Keep LiteLLM's native CLI SSO contract as the primary mechanism. It already meets the 'SSO, short-lived, no sk- keys' goal. The work is to make it robust and invisible. Priority order:

P0 (adopt option A):
- Store the discovered endpoints in the Session and remove the discovery call from refresh/revoke (litellm.py:287, 315).
- Replace the sticky `refresh_pending` lockout with safe-retry rules. Keep the refresh token on connect errors, timeouts, 429 and 5xx/503; require re-login only on 400 invalid_grant or 401 invalid_client. LiteLLM claims the single-use marker only after a successful mint, and a reused native refresh token just returns invalid_grant without revoking the grant.
- Refresh early (remaining < max(10 min, 25 %) and always before an agent launch), so one failed refresh never takes away the current token.
- Re-read the vault after taking the lock, and make the lock wait longer than the worst-case refresh time.

P0/P1 (adopt option B): make every agent pull tokens instead of receiving a static env var.
- Claude CLI `run`: use apiKeyHelper via `--settings`, as the VS Code path already does.
- Codex: `model_providers.<id>.auth.command` (with refresh_interval_ms) instead of `env_key`.
- OpenCode: a tiny global plugin using the `chat.headers` hook.
- These can live in one-time user-level config, which lets the CLI-wrapping layer shrink.
- Then ask the gateway admin to set LITELLM_CLI_JWT_EXPIRATION_HOURS to a few hours (the default is 24 h) and to run Redis for multi-worker deployments.

P1: add paste-back of the redirect URL for `--no-browser` so SSH, devcontainer and Codespaces logins work without port forwarding.

P2: for remote and container development, add an opt-in local token agent with socket forwarding (option C), so refresh tokens stay in the laptop keyring. Add an explicit `--storage file|memory` opt-in (option D) for headless single-user hosts.

Do not delegate wholesale to `lite` (option E). Its single machine-wide credential and lack of tag and team binding conflict with the per-profile/per-customer model, but copy its refresh semantics.

Track option F (IdP-native JWT auth / RFC 8693 token exchange) as the strategic alternative if the company standardizes on Entra or Okta. It needs the same Enterprise license that SSO for more than 5 users already requires. It gives device-code login, IdP-driven offboarding and reuse of existing IdP sessions, at the cost of gateway JWT configuration.

Reject options G (LiteLLM's Claude Code gateway: Claude only, daily re-login, first team only) and H (no device grant in LiteLLM's native contract) as primary answers.

## OPEN QUESTIONS
- Does the gateway run several workers or replicas, and is Redis configured? Without it, single-use refresh and revoke are per-worker only.
- What access-token lifetime does the company want? Today it is the 24 h default. Shortening it is only safe after option B ships for every agent.
- Which IdP is used (Entra ID, Okta, Google)? This decides how practical option F is (verifiable access-token audience, Entra group overage, reuse of `az account get-access-token`).
- Will LiteLLM document and stabilize the RFC 8693 token exchange and move the native contract out of `_experimental`? Will the beta label and EXPERIMENTAL_UI_LOGIN requirement be dropped? Worth asking BerriAI.
- How many developers use SSH remotes, Dev Containers, Codespaces or WSL? This sets the priority of options C and D versus paste-back login alone.
- Does `chat.headers` in OpenCode override the Authorization header set by @ai-sdk/openai-compatible from `options.apiKey`? Needs a live test.
- Does the official Claude Code VS Code extension honour a gateway /login session, and does ANTHROPIC_CUSTOM_HEADERS still apply on gateway sessions? This only matters if option G is reconsidered.
- Does the LiteLLM native consent UI expose the server-side `delivery=manual` (copyable callback URL) option for loopback clients on another machine? It exists in gateway_dcr_flow.py but no UI hook was found.

## OPTION FEASIBILITY
- [yes] A. Harden the existing native-contract client: The server semantics support every proposed change. The claim comes after the mint, 503 temporarily_unavailable leaves the token valid, and a replayed native refresh token gets only 400 invalid_grant with no grant revocation (gateway_dcr_flow.py). Storing the endpoints follows lite's record (cli_sso.md 'The stored credential'). Corrections: a bad client_id on refresh returns 400 invalid_grant, not 401 invalid_client (401 appears only on token exchange), so treat any 400 invalid_grant/invalid_request as terminal. For A5 paste-back, the redirect-path code lives only 120 s. The server also has delivery=manual (300 s, a page showing the callback URL) for loopback clients on another machine, so support pasting either URL. The client's Host-header check (litellm.py:161) does not affect paste-back. Developer interaction: one-time per machine.
- [yes] B. Transparent renewal through each agent's own credential hook: Claude: apiKeyHelper is allowed in --settings ('Any file' scope). It re-runs on TTL (default 5 min) and on 401/403 only when ANTHROPIC_AUTH_TOKEN is unset, so agents.py:104 must stop setting it. The JWT-expiry trigger does not apply because LiteLLM tokens are opaque. Codex: auth.command is confirmed in rust-v0.160.1 and is mutually exclusive with env_key (validated in model-provider-info/src/lib.rs). It re-runs lazily after refresh_interval_ms and once on 401. env_http_headers for the customer tag can stay. OpenCode: chat.headers is merged last as per-call headers, and AI SDK combineHeaders lets those override the provider's 'Authorization' (exact key case required). The behaviour is source-confirmed, not live-tested. Developer interaction: none after the one-time login. The configs can live in one-time user-level files (~/.codex/config.toml, an OpenCode global plugin).
- [uncertain] C. Local token agent with socket forwarding: Technically sound: ssh RemoteForward of a Unix socket and devcontainer bind mounts both exist. No primary source was checked for VS Code or Codespaces automatic socket forwarding, so per-environment setup is likely. It adds daemon lifecycle work on three OSes. The server's delivery=manual login mode removes part of the remote-login motivation. Keeping refresh tokens off remote hosts is still a valid security reason. Developer interaction: one-time per machine, plus a per-repo devcontainer line.
- [yes] D. Explicit storage fallbacks (owner-only file or memory): Matches lite's own behaviour: the key and refresh token fall back to ~/.litellm/token.json (0600) when no keychain is usable (cli_sso.md). It also matches kubelogin's disk|keyring|none and GCM's plaintext/gpg/cache stores. The az and gh specifics were not verified. Make it opt-in, because a file-stored refresh token is a 14-day sliding credential. Developer interaction: one-time per machine.
- [no] E. Delegate auth to LiteLLM's own CLI: Feasible as a token source, but not as described for this user. lite stores one credential per machine (keychain litellm-cli/credential), so several business-unit teams cannot be held at once. Its wrappers and config writers now inject static ANTHROPIC_AUTH_TOKEN and strip apiKeyHelper (lite README:511,537), which works against goal 2 for long sessions. Copying its refresh semantics (360 s buffer, keep the key on failure, sibling re-read) is the right takeaway, and the researcher already recommends that.
- [uncertain] F. IdP-native tokens with LiteLLM JWT/OIDC auth, optionally via RFC 8693 exchange: Source supports it: enable_jwt_auth plus JWT_PUBLIC_KEY_URL/issuers, x-litellm-team-id per request (handle_jwt.py:1915+), and token exchange available only under jwt_auth, DB, license and no virtual-key mapping (idp_token_exchange.py:49-50). The Okta tutorial uses an apiKeyHelper with device code and refresh. Blocking unknowns: the token exchange is undocumented, it needs a gateway-DCR client_id, and Enterprise licensing is required. Reusing `az account get-access-token` is plausible but depends on the IdP app registration and audience. Developer interaction: one-time per machine, or none if an IdP session is reused.
- [no] G. LiteLLM 'Claude Code Gateway': The researcher's reject is correct: there are no refresh tokens (401 invalid_grant on refresh), the token gets the first team only, it is Claude-only, and it cannot coexist with apiKeyHelper or ANTHROPIC_AUTH_TOKEN (llm-gateway-connect troubleshooting table).
- [no] H. Device authorization grant against LiteLLM's native contract: Not supported (cli_sso.md Security rules). The headless need is better met by the server's delivery=manual copy-callback-URL mode for loopback clients (gateway_dcr_flow.py:918-960), which the researcher only listed as an open question.
