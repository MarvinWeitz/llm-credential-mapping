## RECOMMENDATION
Adopt option A: replace the Custom Endpoint bridge with a small private extension that implements the stable LanguageModelChatProvider API (vendor 'litellm-sso'). The quickest route is to fork the MIT extension in BerriAI/litellm/vscode-extension and swap its static virtual key for the CLI's SSO session.

How it should work:
- **Token:** call a new `llm-credentials token --json` (the same idea as the existing Claude apiKeyHelper), cache the token in memory until shortly before expiry, and retry once on a 401.
- **Customer:** take it from the window's workspace. Order: a committed `llmCredentials.customer` in .vscode/settings.json, then the existing repositories.json binding, then a one-time in-editor picker fed by /tag/list. Show it in the status bar and in the model's detail text.
- **Requests:** send `x-litellm-tags` on every /v1/chat/completions call, and advertise toolCalling so the models appear in agent mode.
- **Distribution:** ship it as a VSIX installed by an `llm-credentials vscode install` command, or through the private marketplace, and allow it with the AllowedExtensions policy.
- **Defaults:** set chat.defaultModel (or the ChatDefaultModel policy) so new chats start on the LiteLLM model. Set chat.byokUtilityModelDefault='Main Agent Model' if utility calls (titles, commit messages) should also be billed to the customer.

Developer interaction drops to one-time per machine (install plus SSO login). The customer becomes one-time per repo, shared by the team, or none if option G maps repos centrally. Short-lived SSO is kept: no sk- keys, no pasted local key, no foreground process, no port, no per-customer registrations.

Keep option B only as a temporary fallback where extensions are blocked. Even then, use `requestHeaders` for the tag and auto-start the bridge; the customer remains a manual per-chat choice there.

Reject options C, D, E and F: each either needs static keys or cannot vary the customer by repo.

Before rollout, pilot three things:
1. The org's 'Bring Your Own Language Model Key in Select IDEs' policy is on.
2. SSO session tokens are accepted on /model_group/info or /v1/models.
3. Remote/Dev Container behaviour with the chosen extensionKind.

What cannot be routed under any option: inline suggestions/NES, embeddings and semantic search always go to GitHub-hosted models.

## OPTION FEASIBILITY
- [yes] A. Private VS Code extension (stable LanguageModelChatProvider), CLI SSO token, customer from the workspace: Confirmed in source and docs: the stable API, automatic activation event, BYOK marking of extension models, tools forwarded through ExtensionContributedChatEndpoint, per-window extension host, and an MIT base to fork. Caveats: (1) The BYOK policy default is documented inconsistently (v1_117 says on by default; the language-models FAQ and GitHub docs say it 'must be enabled'), so check the org. (2) GitHub responsible-use docs say some agent-mode actions (code application, tool calls) may still use Copilot-integrated models that are not tagged. (3) Whether ChatDefaultModel accepts an extension model id is unverified. (4) Whether CLI-SSO session tokens are accepted on /model_group/info is unverified. (5) Remote/extensionKind 'ui' behaviour is inferred. None of these blocks the core design.
- [uncertain] A2. Extension-native OAuth (AuthenticationProvider + SecretStorage): The VS Code APIs exist (vscode.d.ts L18184 registerAuthenticationProvider, L10927 asExternalUri, L11727 registerUriHandler, L8464 secrets). Unverified: whether LiteLLM's CLI-SSO dynamic client registration accepts a vscode:// or asExternalUri redirect rather than only a 127.0.0.1 loopback. The repo's own flow uses loopback only. Loopback inside Codespaces/containers would need port forwarding. It needs a separate second login.
- [yes] B. Custom Endpoint plus a simplified, auto-started local bridge: requestHeaders with x-litellm-tags works (not reserved). Correction: the 'group-level url discovery' variant cannot carry per-model customer headers, because headers come only from configuration.models entries (customEndpointProvider.ts L156-173), so each customer must be a listed model. A local key is still pasted once per profile, the customer is still chosen per chat, and issue #329545 shows churn. Viable only as a fallback.
- [no] C. Custom Endpoint direct to LiteLLM with the SSO access token as apiKey: apiKey resolves only through SecretStorage (languageModels.ts L2324-2342); a literal in the file is not used. Short-lived tokens cannot be renewed. The rejection is correct.
- [no] D. Upstream LiteLLM extension as-is: package.json configuration requires apiKey 'A LiteLLM virtual key'. There is no SSO and no tag header (gateway.ts). This conflicts with goal 3. Rejection correct; it remains a good fork base.
- [no] E. GitHub enterprise/org BYOK (server-side custom models): An org-held static key, called by GitHub's Copilot API (public preview). No per-developer SSO identity and no per-repo tag. Rejection correct.
- [no] F. Per-customer profiles, or the CLI rewriting chatLanguageModels.json: The file is per profile (languageModelsConfigurationService.ts L60), so concurrent windows on different repos conflict. Profiles are heavy. Rejection correct.
- [yes] G. Gateway-side repo-to-customer mapping via async_pre_call_hook: The hook exists (custom_logger.py L413), and tags are merged in litellm_pre_call_utils.py before hooks run. It needs custom gateway code, and the repo identity is still reported by the client. A good complement to A for 'none' interaction on mapped repos.
