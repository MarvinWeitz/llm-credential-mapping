# session-project
## VERDICT
There is no direct way. At 10444df (and on upstream main d364d5e), a native CLI SSO session token has no project at all, so project budgets, models, blocked state, tags, guardrails and project spend never apply to requests sent with it. No minting path sets a project. The per-request refresh re-reads only the user and team. The consent page and the sealed grant hold only team_id. No header, body or metadata field lets a request pick a project, and caller-supplied user_api_key_* metadata is stripped. Project checks run only when the authenticated token's project_id is set, and only a virtual key can have one. There are two indirect routes, and both work by turning the SSO identity into a virtual key that has a project_id. (A) Supported today and fully automatable: the client CLI uses its session token to call POST /key/generate with team_id, project_id and a short duration, then sends LLM traffic with the sk- key it gets back. Nobody pastes or rotates keys by hand, but sk- bearer keys do exist on the developer's machine. The developer must be allowed to call /key/generate for the team: by default team members with role "user" may only call /key/info and /key/health, while team admins pass. (B) JWT-to-virtual-key mapping (enterprise): the client sends the raw IdP JWT, not the LiteLLM session token. A configured claim maps to one admin-created virtual key, and that key can carry a project_id. It is one claim value to one key to one project, so there is no per-request project choice. Only proxy admins can manage mappings, auto_register never sets a project, and turning mapping on disables the RFC 8693 token exchange. So "Projects don't work with SSO" is correct for the session credential itself. Projects do work in an SSO setup once each project's traffic goes through a key bound to that project.

## RISKS
- Requests sent with an SSO session token are attributed only to the user and team. Project budgets, models, blocked state, tags, guardrails, model_config and project spend are skipped completely, with no error.
- Workaround A (session token mints a key via /key/generate with project_id, team_id and duration) still creates sk- bearer keys on developer machines. No one handles them manually, but the client must store them securely, delete or let them expire, and mint one key per (developer, project). Each key belongs to one project for life.
- Workaround A needs team_member_permissions to include /key/generate, or the developer to be a team admin. Also, the server does not check that the project belongs to the key's team (inferred from missing code). The client CLI or a policy layer must stop keys from being bound to the wrong team's project. Otherwise spend can be split between team X and a project owned by team Y.
- Workaround B (JWT-to-virtual-key mapping) means LLM traffic carries the raw IdP JWT, not the LiteLLM session token. It needs an enterprise license and enable_jwt_auth, and only proxy admins can maintain the mappings. It gives one key and one project per claim value, so no per-request project choice unless the IdP issues different claim values per project. It disables the RFC 8693 token exchange. The mapped key is a long-lived database key, since auto_register_map_existing_key reuses only non-expiring keys. Mapping changes take up to virtual_key_mapping_cache_ttl (300s by default) to take effect.
- auto_register never assigns a project, so it cannot attribute anything to a project automatically.
- Not fully traced: whether internal_user route checks allow /key/generate for every session-token caller. This is inferred from the session-token-specific branches in key generation.
- The local checkout is depth 1, and gh API access to BerriAI/litellm is not enabled for this session. History was checked only from 2026-10-01 to 2026-10-07 through a separate blobless clone. Open PRs and issues were not checked.
- Line numbers refer to 10444df. On upstream main, auth_checks.py changed by +488/-? lines and gateway_dcr_flow.py by about 300 lines, so line numbers there differ. No change touches project behaviour.

### CORRECTED VERDICT
The main verdict holds when checked against the source at 10444df. Upstream main is still d364d5e (git ls-remote today), so nothing newer changes it. A native CLI SSO session token never has a project. get_cli_jwt_auth_token builds UserAPIKeyAuth with no project_id (auth_checks.py:3810-3825). The per-request refresh merges only team_grants, user_role and models (user_api_key_auth.py:1452-1490, called at :2051-2058). None of the SSO, DCR, token-exchange, consent or JWT files mention 'project' (grep -ci = 0 in gateway_dcr_flow.py, idp_token_exchange.py, proxy_api_credentials.py, gateway_endpoints.py, native_client_consent.py, ui_sso.py, handle_jwt.py). No request field selects a project. user_api_key_project_id is always copied from the token (litellm_pre_call_utils.py:1637), and caller-supplied user_api_key_* metadata is stripped (:2255-2279). The project row is loaded and enforced only when the token has a project_id (user_api_key_auth.py:2935-2948, :3069-3071; auth_checks.py:740-787, :1168-1177). So with a session token, project budgets, models, blocked state, tags, guardrails, model_config and project spend never apply. They also never raise an error.

Projects can still work in an SSO setup, but only when the request carries a credential that has a project_id. There are three ways to get one.

(A) Supported and fully automatable today. The client CLI uses the session token to call POST /key/generate with team_id, project_id and a short duration, then sends LLM traffic with the sk- key it gets back. The route layer allows this for internal users: internal_user_routes includes key_management_routes (_types.py:706-731, :897-923; route_checks.py:328-330). The real gate is team membership. A team member with role 'user' gets only /key/info and /key/health by default (team_member_permission_checks.py:18-23, :105-133), so the team must grant /key/generate or the developer must be a team admin. The new key is auto-assigned to the developer's user_id (key_management_endpoints.py:2099-2104), so attribution covers user, team and project. The CLI can find projects through /project/list and /project/info, which internal users and team members can call (_types.py:913-914; enterprise project_endpoints.py:967-1035).

(B) Enterprise JWT-to-virtual-key mapping. The client sends the raw IdP JWT. One admin-managed claim value maps to one key, and through it to one project. There is no per-request choice, and enabling it turns off the RFC 8693 token exchange.

(C) Missed by the investigator: a custom auth hook. Set general_settings.custom_auth, plus custom_auth_run_common_checks, or enable_post_custom_auth_checks for the post-auth checks. The operator's function can return a UserAPIKeyAuth with project_id, and the centralized checks then fetch and enforce the project (user_api_key_auth.py:1590-1622, :2873-2878, :2935-2948, :3972-3981). In principle such a hook could decode the session token and read a project header after checking team membership. But it bypasses _refresh_session_token_grants and the built-in session-token handling, so it is custom code to maintain, not a LiteLLM feature. Whether it works end to end is inferred, not tested.

Two corrections to the findings.
1. Per-request tags are not merely 'not enforced'. Header and body tags feed _tag_max_budget_check, so tag budgets are enforced and tag spend is tracked (auth_checks.py:1193-1210, :1278-1284, :6571-6640). The caller still chooses whether to send them, so they cannot replace a mandatory project binding.
2. The inferred missing check that a project belongs to the key's team is confirmed by open upstream PR #44165, which also shows a fix is coming. Once it merges, project-bound keys must use the project's own team_id. A key with no team will be rejected for a project owned by a team.

Projects as a whole are enterprise-only. The endpoints live in the enterprise package, and create, update and delete are all premium-gated.

On the user's question: 'Projects don't work with SSO' is accurate only for the SSO session credential itself. 'Team BU CP > project smart > customer X' maps cleanly onto Projects once the developer's CLI turns the session token into a short-lived key bound to that project (pattern A).
