# mint-project-keys
## VERDICT
Feasible, but not with default settings, and the code has a real cross-team gap that has to be closed before using it.

(a) By default a plain team member (team role "user") is refused with 401 "Team member does not have permissions for endpoint: /key/generate". The reason is that team_member_permissions defaults to [], which leaves only /key/info and /key/health. Two things are needed: (1) the developer's global role must be internal_user, because internal_user_viewer, the SSO default when no role is mapped, cannot reach /key/generate at all; and (2) a team admin or proxy admin must add "/key/generate" to BU CP's team_member_permissions. A team admin of BU CP can already mint keys today. Once both are in place, the session token mints the key: user_id is stamped automatically, `duration` sets `expires`, and admins can cap the duration (upperbound_key_generate_params.duration, or team metadata team_member_key_duration).

(b) Nothing checks that project.team_id equals the key's team_id, or that the caller belongs to the project's team. This holds both when the key is minted and when it is used. A member of any team can bind a key to any project_id they know. A personal key (no team_id) can do the same and skips the team-permission check entirely. That is a cross-team attribution and budget-burn gap. It has to be closed with a general_settings.custom_key_policy hook, and/or by restricting personal keys (key_generation_settings.personal_key_generation.allowed_user_roles=["proxy_admin"]).

(c) Yes: user_id and created_by are recorded on the key and in spend logs.

(d) Yes, duration is honoured and can be capped by admins. One loophole: an explicit "duration": null on /key/update makes the key never expire and gets past the upperbound cap. Only callers allowed to update the key can do this.

(e) Listing and deleting your own keys works by default. Regenerate needs a premium licence, plus the /key/regenerate team permission for team members.

(f) Expired keys are never deleted automatically. The only cleanup job covers dashboard UI session keys and is opt-in, so the CLI must delete its own expired keys.

(g) The generate path itself has no premium check, but creating projects is Enterprise-only.

(h) There is no limit on the number of keys per user or team, and no rate limit on minting. key_alias must be unique across all keys.

Recommendation: use it, with explicit team_member_permissions, upperbound/team key duration, a custom_key_policy that enforces project.team_id == key.team_id (and that the caller is a member), personal-key minting locked down, and the CLI cleaning up its own keys.

## RISKS
- SECURITY GAP (confirmed in source): no check that project.team_id == key.team_id, or that the caller belongs to the project's team, at mint time or at request time. Any internal_user who knows a project_id can mint a key bound to another team's project. A personal key (no team_id) bypasses team_member_permissions entirely. Result: cross-team or cross-customer misattribution and burning another project's budget. Mitigate with a custom_key_policy hook (look up the project, require effective_key.team_id == project.team_id and effective_key.user_id to be a member), and/or key_generation_settings.personal_key_generation.allowed_user_roles=['proxy_admin'] plus team_key_generation.required_params=['project_id','duration'].
- Default config does not work: team_member_permissions defaults to [] (only /key/info, /key/health), and SSO users default to internal_user_viewer, which cannot call /key/generate. Both must be changed. Granting '/key/generate' applies team-wide to all role-'user' members, and members can then mint keys with any duration up to the upperbound.
- Max duration can be bypassed on /key/update with an explicit "duration": null (never expires), because the upperbound check skips None on update. Applies to callers with update rights (creator/owner, team admin, members granted /key/update). Do not grant /key/update, and add a custom_key_policy that rejects expires=None or expires too far out.
- Minted sk- keys are independent bearer secrets. They outlive the SSO session and `lite logout` (which revokes only the refresh token), and persist on disk on the dev machine until they expire or are deleted. Removing a user from the team deletes their team keys, but IdP deprovisioning alone was not shown to revoke them (not traced: SCIM user delete).
- Expired keys accumulate in LiteLLM_VerificationToken (no automatic cleanup for non-dashboard keys), and deleted ones move to LiteLLM_DeletedVerificationToken. key_alias must be globally unique (expired keys included). No per-user key count or mint rate limit exists, so a buggy CLI loop could flood the table. The CLI should reuse a still-valid key and delete expired ones (/key/list?project_id=...&status=expired, then /key/delete).
- Key metadata sent by the client is caller-controlled. Keep 'customer X' in project.metadata (admin-only via the Enterprise /project/update), not in key metadata.
- Not executed end-to-end. Conclusions come from code-path reading plus existing unit tests of _common_key_generation_helper. Not traced: the ordering of apply_user_info_values_to_sso_user_defined_values versus default_internal_user_params for the effective SSO role; whether rate limiters apply to management routes (inferred no); behaviour of keys whose project is deleted.
- Projects and /key/regenerate require an Enterprise licence. The open-source generate path accepts project_id, but projects cannot be created without premium.

## REVIEW verdict_holds=yes
### CORRECTED VERDICT
The verdict holds. A short-lived, project-bound key minted by the CLI from the SSO session is feasible, but not with default settings, and there is a real cross-team gap that a hook must close before relying on it.

- **Default behaviour:** a plain team member (team role "user") with a CLI session token is refused on POST /key/generate with a team_id. team_member_permissions only covers /key/info and /key/health by default, and the refusal is a ProxyException with code 401 (litellm/proxy/management_helpers/team_member_permission_checks.py:18-23, 116-132; key_management_endpoints.py:653-657, 2124-2129).
- **What has to change:** the developer's global role must be internal_user, because internal_user_viewer does not get key routes (_types.py:897-941; route_checks.py:327-364). A team admin or proxy admin must also add "/key/generate" to BU CP's team_member_permissions.
- **What then works:** the session token is re-validated against the DB on every request (user_api_key_auth.py:1450-1491, 2051-2058). user_id is forced to the caller (2093-2102). The project must exist and the key's models and max_budget must fit inside it (1764-1811). duration becomes expires (4638-4643). upperbound_key_generate_params.duration caps it (1164-1176).
- **The gap:** nothing checks that project.team_id equals the key's team_id, or that the caller belongs to the project's team. This is missing at mint time (the only project check in generate is 1764-1811) and at request time (auth_checks.py:742-785). It is still missing on upstream main d364d5e. Personal keys with a project_id do not need any team permission (_personal_key_generation_check, 723-762; dispatched at 805-807), so any internal_user who knows a project_id can attach spend to another team's (and so another customer's) project.
- **Mitigations:** a general_settings.custom_key_policy hook (not premium-gated; it receives effective_key, including project_id, on generate, update and regenerate, 1347, 3521, 5637), plus key_generation_settings that restrict personal keys and require project_id and duration.
- **Licence:** projects can only be created or updated with an Enterprise licence (enterprise project_endpoints.py:494-498, 686-690), so the design needs one in practice.

Corrections and refinements to the investigator's answer:
1. **SSO role ordering (they left this untraced; resolved).** get_user_info_from_db inserts the new user first (ui_sso.py:1832 -> upsert_sso_user 3276 -> insert_sso_user 3305, which applies default_internal_user_params at 2633-2646). apply_user_info_values_to_sso_user_defined_values (3631) runs afterwards and takes the DB role. So default_internal_user_params.user_role=internal_user does take effect for newly created SSO users. Existing users keep their DB role unless the IdP or role mapping supplies one.
2. **team_member_key_duration overrides the requested duration, and it runs after the upperbound check.** apply_enterprise_key_management_params (1335-1344) runs after _enforce_upperbound_key_params (1271). A team-metadata duration therefore silently replaces the CLI's "8h" and can exceed the upperbound cap.
3. **Upstream changes in the files the investigator did not check.** project_endpoints.py and auth_checks.py did change on main d364d5e. The project info/list visibility logic was reworked (_can_view_team_projects, org admins). Nothing was added that ties a key's project to its team, and the premium gates are unchanged.
4. **Small precision points.** LiteLLM_ProjectTable.team_id is nullable in the schema, but /project/new requires team_id (enterprise project_endpoints.py:414, 519). Team admins can create projects only if general_settings allows it (team_admin_may_manage_projects, team_admin_field_permissions.py:97-100).

Risks to state to the user:
- the cross-team project-binding gap;
- minted sk- keys are independent bearer secrets that outlive SSO logout or IdP deprovisioning until they expire or are deleted;
- the "duration": null path on /key/update produces a non-expiring key (2518-2521 together with 1145-1149);
- expired keys pile up because nothing deletes them automatically (the cleanup job covers UI session keys only and is opt-in);
- key_alias must be unique across all keys;
- there is no limit on how many keys a user can mint.
