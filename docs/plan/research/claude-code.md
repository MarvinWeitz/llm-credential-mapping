## CURRENT ASSESSMENT
- `llm-credentials run claude` passes a static ANTHROPIC_AUTH_TOKEN to the child (agents.py:102-105, with env built in agents.py:33-48). Claude Code only re-fetches on 401/403 or JWT expiry when the credential comes from an apiKeyHelper and ANTHROPIC_AUTH_TOKEN is unset, so a long CLI session can never renew its token. The README admits this ('a running agent is not automatically reauthenticated').
  IMPACT: Breaks goal 2 for long CLI sessions and forces a per-session launch through the wrapper. Claude Code already has the right mechanism (apiKeyHelper); the CLI path just doesn't use it.
  FILES: src/llm_credential_mapping/agents.py:33-48,102-105; README.md:236-242
- The VS Code extension integration works but is heavy. It uses `claudeCode.claudeProcessWrapper` pointing at a second console entry point (pyproject.toml:18). That entry point resolves the repo from cwd or --project-config-root (claude.py:305-328), pins a JSON context in an env var (claude.py:47-79), rewrites argv and injects `--settings` with apiKeyHelper, env overrides, model and modelPicker (claude.py:229-292), then execs or job-object-supervises the bundled binary (claude.py:295-302; windows_process.py:44+). Supporting it takes a 403-line JSONC editor for VS Code settings (editor_settings.py) and a 101-line workspace mapping store (workspaces.py).
  IMPACT: About 1,000 lines of code exist only to put env vars and an apiKeyHelper into a process that already reads ~/.claude/settings.json and the project's .claude/settings*.json. Documented side effects of the wrapper: wrapped conversations start in Manual permission mode, and the 'conversation open elsewhere' check is skipped. There are also host risks: Windows application policy blocking pip .exe launchers, and Linux D-Bus propagation (README.md:540-575).
  FILES: src/llm_credential_mapping/claude.py:145-170,229-292,295-378; editor_settings.py; windows_process.py; workspaces.py; pyproject.toml:18
- The helper side is already right. claude.py:278 sets an apiKeyHelper that only prints the token, and the CLI already has a suitable standalone `llm-credentials token --profile X` (cli.py:308; README 'Credential-helper output'), which renews when 60 s or less remain and never opens a browser. However, the extension's `claude token` helper depends on the wrapper-pinned context (claude.py:191-198), and the TTL is forced to 60 s (claude.py:271).
  IMPACT: The pinned-context helper is only needed because of the wrapper. A plain `token --profile` helper set once in ~/.claude/settings.json would serve both the CLI and the extension. The 60 s TTL is unnecessary on Claude Code 2.1.246 or later (it refreshes expired JWTs before sending and retries on 401/403).
  FILES: src/llm_credential_mapping/claude.py:191-207,271,278; cli.py:308; sessions.py:53-67
- Customer assignment is one-time per repo per developer: a local repositories.json maps Git origin to tag (repositories.py:128; request_context.py:28-43). In the extension, an unbound repo fails closed with 'run repo bind in a terminal' (request_context.py:41), because the interactive picker exists only in `run` (cli.py:323). Parent-folder workspaces need a separate `claude workspace bind` (workspaces.py:67-87).
  IMPACT: Interaction rating: one-time per repo per developer, plus extra per-workspace steps for parent folders. Sharing bindings by origin across clones and worktrees is good. Nothing is shared across the team, and the binding is invisible to Claude Code itself, so only the wrapper can apply it.
  FILES: src/llm_credential_mapping/repositories.py:54,128; request_context.py:28-43; cli.py:110,318-330; workspaces.py:67-87
- The model is pinned to one alias: every ANTHROPIC_*_MODEL variable plus modelPicker.replaceBuiltInOptions (claude.py:26-30,273,279-287), and `claude setup --model` is required.
  IMPACT: Developers can't pick models without rerunning setup. Claude Code now has native gateway model discovery (`CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1`, which reads LiteLLM /v1/models filtered per user/team). Alternatively, naming LiteLLM aliases with Anthropic model IDs needs no client model config at all.
  FILES: src/llm_credential_mapping/claude.py:26-30,273,279-287
- Known refresh bug: the refresh path does a discovery GET before sending the refresh token, and it marks refresh_pending first. A transient network error therefore forces a browser re-login.
  IMPACT: Under any helper-based design (recommended below), many Claude processes call the helper on their TTL and on every 401/403. A spurious lockout then interrupts every open session, so fixing this becomes a prerequisite: cache discovery and only set pending immediately before the refresh POST.
  FILES: src/llm_credential_mapping/sessions.py:61-67; litellm.py:286

## RECOMMENDATION
Adopt option A for both Claude surfaces, and roll its base config out with option C where you have MDM. Drop the claudeProcessWrapper approach and `run claude`.

Minimal configuration. (1) ~/.claude/settings.json, or the managed-settings.json/managed-settings.d drop-in, without the tag:
{"apiKeyHelper":"/home/dev/.local/bin/llm-credentials token --profile consulting","env":{"ANTHROPIC_BASE_URL":"https://litellm.example.com","CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY":"1","CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC":"1"},"hooks":{"UserPromptSubmit":[{"hooks":[{"type":"command","command":"/home/dev/.local/bin/llm-credentials claude guard"}]}]}}
On Windows use "apiKeyHelper":"\"C:\\Users\\dev\\.local\\bin\\llm-credentials.exe\" token --profile consulting".
(2) Per repo, written by `llm-credentials repo bind` (or auto-written by the guard when repositories.json already knows the origin): <repo-root>/.claude/settings.local.json = {"env":{"ANTHROPIC_CUSTOM_HEADERS":"x-litellm-tags: customer-acme"}}. The file must also be excluded from git.
(3) VS Code user settings, once: {"claudeCode.disableLoginPrompt": true}.
(4) Models: name the LiteLLM model aliases with Anthropic IDs (the model IDs Claude Code knows) so no ANTHROPIC_*_MODEL variables are needed; discovery lists the models the team is allowed to use. If custom aliases are unavoidable, use user- or managed-level `modelPicker` rows with `behavesAs`.

Interaction: one-time per machine (setup and login) plus one-time per repo per developer. This drops to none when a central origin-to-customer mapping lets the guard auto-bind (option G).

What becomes unnecessary:
- the `llm-credentials-claude` entry point (pyproject.toml:18);
- most of claude.py (wrapper_main, wrapped_command, project_directory, ClaudeContext, helper_token, verify_wrapper);
- windows_process.py;
- workspaces.py (write settings.local.json into the launch folder instead);
- editor_settings.py for the Claude path (only one boolean remains);
- the claude branch of agents.py (the one-off customer override is `claude --settings '{"env":{"ANTHROPIC_CUSTOM_HEADERS":"x-litellm-tags: other"}}'`, tested).

Keep login, token, sessions, storage, repositories and tags, and add a small settings.local.json writer plus the guard command. Fix the refresh-pending/discovery bug first, because every Claude process now calls the helper on its TTL and on each 401/403. Accept, and document, that rebinding now retags running sessions instead of pinning per process.

Watch option D, LiteLLM's native Claude Code gateway sign-in. It removes all local auth code for Claude, but today it needs admin-deployed managed settings and a private-address gateway, and it has no refresh tokens (re-login about daily). Revisit it once LiteLLM issues refresh tokens and it is confirmed that ANTHROPIC_CUSTOM_HEADERS and the VS Code extension work with gateway sessions.

## OPTION FEASIBILITY
- [yes] A. Native Claude Code settings, no wrapper: a user-level apiKeyHelper and env, a per-repo .claude/settings.local.json written by `repo bind`, and a UserPromptSubmit guard: Every mechanism is documented and I reproduced the core on 2.1.291 with an isolated config dir: the local file is read from a subdirectory, a 401 makes the helper rerun and the request retry, the guard blocks an untagged repo with zero gateway requests, and a user-level default applies outside repos. One correction to the researcher's cons: 'the helper did not receive project env' is only true for the first run. The rerun after the 401 saw the merged ANTHROPIC_CUSTOM_HEADERS=customer-acme plus a project-only variable, so helper env varies across runs and nothing should depend on it. Still unverified for the extension: (1) that disableLoginPrompt plus a ~/.claude apiKeyHelper passes the extension's login check (the docs recommend claudeCode.environmentVariables for credentials); (2) that the extension's SDK host loads local/project settingSources (permissions.md says SDK sessions use project env when project settings are loaded); (3) which folder becomes the launch directory in multi-root workspaces. On Windows the local file is kept in the starting directory (settings.md), so a CLI launch from a subdirectory is blocked by the guard. Developer interaction: one-time per machine, plus one-time per repo per developer.
- [yes] B. Committed .claude/settings.json per repo carrying ANTHROPIC_CUSTOM_HEADERS: Works as described. The shared file is read only from the primary working directory (settings.md), so a CLI launch from a subdirectory sends no tag; VS Code at the repo root is fine. It applies after trust in interactive mode and immediately in -p/SDK mode. The blocker is policy, not technology: it writes an internal billing tag into customer repos. A local file overrides it, so it is spoofable, as today. Developer interaction: one-time per repo, shared by the team.
- [yes] C. Fleet rollout via managed settings for the base config: Documented: managed-settings.json/managed-settings.d or MDM, allowedProviders customEndpoint with a managed env pin (v2.1.285+). Server-managed (claude.ai) delivery does not apply when ANTHROPIC_BASE_URL points away from Anthropic (managed-settings.md, source order). Correct that ANTHROPIC_CUSTOM_HEADERS must stay out of managed env. The researcher overstates the lock: a developer can still export ANTHROPIC_AUTH_TOKEN, which outranks apiKeyHelper. Developer interaction: none for the base config (admin access needed); the per-repo tag still needs A, B or G.
- [uncertain] D. LiteLLM native Claude Code gateway sign-in (/claude_code_gateway, forceLoginMethod gateway): It does not fit the goals today. It needs managed-only keys (forceLoginGatewayUrl has no user-level or URL-field fallback), a gateway hostname that resolves to private addresses only, and LiteLLM rejects refresh_token grants (gateway_endpoints.py:344-350), so developers re-login every CLI_JWT_EXPIRATION_HOURS (24 h by default). The team is fixed to teams[0]. No document mentions VS Code extension support for gateway sign-in. Whether ANTHROPIC_CUSTOM_HEADERS is sent in gateway sessions is unverified. 'Watch, not adopt' is right.
- [yes] G. Hook-driven auto-binding (SessionStart or UserPromptSubmit hook writes settings.local.json from a central mapping): Reproduced independently. A user-level SessionStart hook wrote repoC/.claude/settings.local.json, but the first request of that `claude -p` session went out with no x-litellm-tags, and the next session was tagged `customer-auto`. Hooks run without a TTY (hooks.md), so no interactive picker is possible. Developer interaction: none for known origins, otherwise one-time per repo per developer.

Status quo claudeProcessWrapper + run claude: It works, but the CLI path really does lose renewal: agents.py:104 sets ANTHROPIC_AUTH_TOKEN, which per the docs disables the 401 and JWT-expiry helper reruns and takes precedence over apiKeyHelper. ## MISSED OPTIONS
- Managed `policyHelper` (settings-reference.md#policyhelper, https://code.claude.com/docs/en/settings-reference#policyhelper). It is an admin-deployed executable that Claude Code runs at startup, re-runs every refreshIntervalMs, and whose `managedSettings` output becomes the session's managed tier. In principle it could compute env.ANTHROPIC_CUSTOM_HEADERS from the launch directory's git origin plus a central mapping, together with apiKeyHelper and the base URL, with no per-repo files. That would make the interaction 'none' for known repos, with no first-request race. Caveats: it is documented as running 'with no arguments' and the cwd is not documented (inferred to be the session cwd, untested here because it needs /etc/claude-code). A failed or timed-out run refuses to start Claude Code, so the helper must serve from a cache. Its output replaces all other managed sources. It needs MDM or admin deployment.
- Gateway-side attribution keyed on `x-claude-code-session-id` (https://code.claude.com/docs/en/llm-gateway-protocol#request-headers). A SessionStart hook, which receives session_id and cwd in its JSON input (hooks.md), registers the session id together with the git origin at a small LiteLLM endpoint or custom pre-call hook. The gateway then stamps the customer tag server-side from a central origin-to-customer mapping. This avoids writing settings files and the first-request env-reload race (the registration only has to finish before the first model request; SessionStart hooks finish before Claude's first response). It also moves the mapping server-side. Inferred design, not tested; it needs custom LiteLLM code.
- Setting ANTHROPIC_BASE_URL (and optionally CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY) in `claudeCode.environmentVariables`, as llm-gateway-connect.md#vs-code-extension recommends, instead of relying only on disableLoginPrompt plus ~/.claude/settings.json. The documented reason is that the extension checks credentials from that setting before launch. The guard approach is unaffected because ANTHROPIC_CUSTOM_HEADERS still comes from settings files, which override process env (settings-reference.md#how-env-values-interact-with-your-shell).
