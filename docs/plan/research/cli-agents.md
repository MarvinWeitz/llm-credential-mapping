## CURRENT ASSESSMENT
- The access token is fetched once at launch and frozen into the child's environment. No tool can renew it. cli.py:330 calls token() once; agents.py:99 sets VKM_TOKEN, agents.py:107 sets OPENAI_API_KEY, agents.py:115 points Codex env_key at it, and agents.py:140 points OpenCode apiKey at {env:...}. The README says so too (README.md:239-243: 'a running agent is not automatically reauthenticated').
  IMPACT: Long Codex or OpenCode sessions start getting 401s once the short-lived access token expires, and the developer has to restart through the launcher. This fails goal 2 ('just works') and works against goal 3: the short-lived SSO token does its job, but it makes long sessions painful.
  FILES: src/virtual_key_mapper/cli.py:330; src/virtual_key_mapper/agents.py:98-148; README.md:239-243
- The bearer token sits in the agent's process environment, so commands the agent runs can read it. All agents get VKM_TOKEN (agents.py:99). Codex also gets OPENAI_API_KEY and OPENAI_BASE_URL (agents.py:107-108), which the custom provider does not need because it reads env_key=VKM_TOKEN (agents.py:115). In Codex's current source, shell_environment_policy defaults to ignore_default_excludes=true. That means variables matching *KEY* and *TOKEN* are passed through to tool shells.
  IMPACT: Model-driven shell commands can read or leak the employee's SSO bearer token. Any OpenAI-SDK script the agent runs is also silently routed to the gateway with the employee token and billed to the pinned customer.
  FILES: src/virtual_key_mapper/agents.py:98-108; codex-rs/config/src/shell_environment_policy.rs:135-136 (upstream)
- Interaction happens every session. Every launch has to go through 'vkm run [--profile P] [--model M] codex|opencode'. OpenCode always needs --model (agents.py:126-127), and the generated provider exposes only that one model (agents.py:142). Typing plain 'codex' or 'opencode' skips the gateway, the customer tag and SSO entirely.
  IMPACT: This misses goal 1 and goal 2. Habit or IDE launches lead to untagged usage, or to usage that goes to the vendor directly.
  FILES: src/virtual_key_mapper/cli.py:95-106, 315-330; src/virtual_key_mapper/agents.py:125-148
- Each developer chooses the customer once per repo. Detection uses the launcher's cwd and Git origin (cli.py:319, repositories.py:54-83). The first run in an unbound repo needs a TTY picker (cli.py:110-131, 322-325), and the choice is stored in a local repositories.json. If the agent is pointed at another directory (codex --cd X, or 'opencode /path'), the tag still comes from the launcher's cwd.
  IMPACT: Every developer repeats the binding for every repo. The tag can be wrong when the agent's working directory differs from where the launcher started. Non-interactive launches fail closed, which is good.
  FILES: src/virtual_key_mapper/cli.py:110-131, 315-325; src/virtual_key_mapper/repositories.py:54-83
- The Codex adapter is correct for today's schema. It defines a custom provider through -c, sets wire_api='responses' (the only value Codex now accepts) and requires_openai_auth=false, and sends the tag with env_http_headers (agents.py:109-122). It does not use Codex's command-backed auth table, which exists exactly for short-lived tokens. env_http_headers silently drops the header when its variable is unset or empty. That is safe today only because the wrapper always sets it (agents.py:101).
  IMPACT: The tagging is sound, but Codex's built-in refresh mechanism goes unused. Any move to global config has to deal with that fail-open header.
  FILES: src/virtual_key_mapper/agents.py:106-124; codex-rs/model-provider-info/src/lib.rs:175-179 (upstream)
- The OpenCode adapter passes the provider inline through OPENCODE_CONFIG_CONTENT. That source ranks above project opencode.json, so a cloned repo cannot redirect the token. That part is good. On v2 the adapter forces --standalone and rejects --server and --attach (agents.py:51-73). This is needed because the v2 CLI attaches to a shared background service by default, and that service reads OPENCODE_CONFIG_CONTENT only when it starts (packages/cli/src/server-process.ts:118; services/server-connection.ts:41-50). The version is detected by parsing 'opencode --version' (agents.py:76-90).
  IMPACT: Isolation is correct, but v2's shared service and attach workflows are blocked. The version-sniffing adapter will need updates whenever OpenCode changes its CLI.
  FILES: src/virtual_key_mapper/agents.py:51-90, 125-148

## RECOMMENDATION
Move from 'wrap every launch and inject a frozen token' to 'configure each tool once, and resolve the token (and for OpenCode the customer) per request'. Keep 'vkm run' as a thin fallback.

(1) Do now, low risk, no change for developers (option 2). In agents.py, stop putting the bearer token in the child env: remove VKM_TOKEN, OPENAI_API_KEY and OPENAI_BASE_URL. For Codex, pass -c model_providers.<id>.auth={command, args=['-m','virtual_key_mapper','token','--profile',P], timeout_ms=30000, refresh_interval_ms below the access-token TTL, e.g. 240000} instead of env_key. Codex reruns the command on that interval and once after a 401, so long sessions survive, and Codex tool shells (which by default inherit *TOKEN*/*KEY* variables) can no longer see the token. Before this, harden the helper. Codex kills the helper at timeout_ms (default 5000 ms). If that happens after sessions.py has set refresh_pending, the developer is forced into a browser re-login. The discovery GET before refresh has the same effect on a transient error. Also add 'token --json' that returns the expiry, for plugins.

(2) Target state (options 3a and 3b, both 'one-time per machine'). Add 'vkm setup codex' and 'setup opencode', idempotent and reversible like 'claude setup'.

Codex: write a managed provider into ~/.codex/config.toml with model_provider='litellm-sso', base_url=<gateway>/v1, wire_api='responses', the auth table above, and env_http_headers={'x-litellm-tags'='VKM_CUSTOMER'}. Codex does not allow model_providers in repo-level .codex/config.toml, so the tag has to come from the environment. Provide a one-time shell hook ('eval "$(vkm shell-init zsh|bash|fish|pwsh)"', option 4) that exports only the non-secret customer for the current repo. Pass a --require-customer-env flag to the helper: Codex silently omits env_http_headers when the variable is missing, and the helper inherits Codex's environment, so it can refuse the token and keep tagging fail-closed.

OpenCode: write a global provider (models synced from /v1/models, no apiKey, so --model is no longer needed) and install a global plugin with two builds. v1 uses the 'chat.headers' hook with worktree from PluginInput. v2.0.24 uses a default export {id, setup|effect} with ctx.session.hook('model.request') and ctx.location.project.directory. The plugin sets Authorization from the cached helper token and x-litellm-tags from the worktree's binding. It fails closed without a binding and attaches the bearer only when the origin is the profile gateway. That removes the --standalone and --server/--attach restrictions and makes plain 'opencode' work.

Result: developers type 'codex' or 'opencode' and get short-lived SSO tokens that renew. The only remaining interaction is the repo-to-customer binding.

(3) To get binding down to 'none', pair this with gateway-side or team-shared mapping (option 7, owned by the project-identification area). Codex already sends Git remote URLs in x-codex-turn-metadata, but that is an unstable compatibility header, so treat it as experimental. Also enforce 'tag required' on the gateway, since every client-side tag can be spoofed or dropped.

Do not build a general loopback sidecar for Codex or OpenCode (option 6): it does not solve how Codex identifies the project, and it adds a daemon and a local confused-deputy risk. Reuse the copilot_bridge pattern only if Gemini CLI or Copilot CLI support becomes a requirement; both take only static env keys and have no token helper.
